The tools of the trade for reliable agents

An agent will never give the same answer twice. Reliable results and behavior mean the answers stay inside a band your team can read, debug, and ship. Three levers narrow that band: the input, the output, and the recovery. This page sorts twenty-three practices by the lever each one pulls. For each one you get the agent behavior it fixes, how to do it, one real example, and how to prove the results changed. The cost: every practice needs measuring, and most charter edits measure as no change at all.

The band

Reliability is a band, not a repeat

You can't make the model deterministic. You can make the workflow deterministic, and then measure how wide the band of results is.

Harness Engineering defines reliability as "variance that stays inside a band you can read, debug, and ship." Each of those three words names one lever. If any one lever is missing, the run feels unreliable, even when the other two hold.

WordLeverWhat it narrowsTools
readNarrow the inputwhat the agent knows before it acts1–7
debugNarrow the outputwhat it may produce and ship8–14
shipNarrow the recoverywhat happens when it fails anyway15–20
all threeThe human rungwhat no predicate or judge can see21–23

How to measure the band

Run the same task set twice: once with a change, once without. Use at least 30 runs per arm, and score each run blind against its intent contract. Then compare the failure rate and the band width. Don't compare the best run. The Eval Loop has the procedure, and tool 18 below is its summary.

The claim this page defends

Filters compose. No single tool here has to be perfect. A gate that catches 80% of its class is still sharp, and each tool removes failures the others let through.

1
Decide

Pick your lever in two questions

First find which word failed. Then find where the control goes. Most bad fixes are a good control at the wrong address.

Question 1 · which word failed?

  1. Couldn't read itThe agent solved the wrong problem, used the wrong words, or copied a bad pattern. Narrow the input: tools 1–7.
  2. Couldn't debug itThe work broke a rule, ran a command it shouldn't, or passed checks and was still wrong. Narrow the output: tools 8–14.
  3. Couldn't ship itThe run crashed, looped, burned budget, or nobody can say why it merged. Narrow the recovery: tools 15–20.

Question 2 · where does the control go?

Apply these rules in order. Stop at the first one that answers.

  1. The code teaches itFix the code before you write a rule. The agent copies code before it obeys prose (tool 4).
  2. Nobody wrote it downWrite it as a contract for one task (tool 1), or as a charter rule for every task (tool 2).
  3. It has "then" in itIt is a sequence, not a rule. Make it a command or a skill (tool 7).
  4. Code can decide itMake it a check. Run the checker; don't ask the model to read the file (tools 10–12).
  5. Only judgment can decide itKeep the prose rule, and add a judge or a human (tools 8, 21).
  6. The agent can reach the enforcerIf the damage is real, move the check out of reach, into the harness (tool 11). Anything the agent can edit is not a control.
  7. It governs what shipsIt belongs in the factory, at a stage gate (tool 19), not in the charter.
  8. You want a second agentAdd one only for separate memory, a separate refusal scope, or a separate tool surface (tool 8).
  9. It's about order of stepsSequencing never goes to a model. Put it in the workflow (tool 19).

Four rules that hold at every address

  • Lowest rung first. Start at the cheapest control that holds. Promote it only after an incident shows it leaks.
  • Cost of being wrong sets the speed. A leaked secret earns a gate on sight, while a style preference earns a linter.
  • The platform sets the floor. Teams can tighten a control and never loosen it (Whose Gate Is It).
  • No move without a measurement. Every promotion and every deletion ships with an eval result (tool 18).

The Journey of a Rule walks one rule through all six homes. Constraint Engineering gives the full model.

2
Input

Narrow the input

What the agent knows before it acts. Instruction is the weakest signal, and the code it imitates is the strongest.

The intent contract

Why
The agent solves a neighboring problem, or the right one at the wrong size. Intent that lives in a private chat can't be checked by the harness, the reviewers, or other agents.
How
Write seven fixed sections: outcome, signal, scope in, scope out, acceptance criteria, risk surface, and open questions. Every criterion must be able to fail, and every open question gets a default. Then sign it before work starts.
Example
"Tests look fine" can't fail. "A new test fails on the merge base and passes on HEAD" can.
Prove it
Count criteria marked not met at review, and contracts reopened after signing. Both fall as contracts get sharper.

Learn more · The Factory · Ghola · Harness Engineering ch. 47–48

The charter

Why
The agent repeats a mistake that is specific to this codebase. A rule stops the repeat, but only if it's true, because a rule the code doesn't follow teaches the agent that rules are optional.
How
Start empty. Add a rule after the third occurrence, or at once if the cost is high. Mark it iron, golden, or preference. Give it a reason with a mechanism and a number, and say what enforces it.
Example
"Use clients.http for every third-party call, never requests. The wrapper sets a 4-second timeout." The reason: an outage held all 16 workers for 23 minutes. The limit: it doesn't catch the 61 files already on the old pattern.
Prove it
Each quarter, check 20 rules against 5 recent files. A rule that holds in fewer than 4 is aspirational: fix the code or demote the rule.

Learn more · Anatomy of a Charter · Migrating Without Lying · Keystone · Harness Engineering ch. 11–12 · The Last Check ch. 21

Context and memory

Why
The agent uses the wrong word, acts on stale facts, or gets worse as the session grows. Each of those comes from what it loaded, so fix what loads.
How
Load reference material on demand, not at start, and keep one meaning per term in a glossary. Derive state from the system of record instead of memory. When nobody knows a rule, ask a person and write the answer down.
Example
Is shipping refunded on an $84.00 order? A question in the support channel got an answer in 11 minutes. It became ADR-014: Shipping is not refunded once the carrier has scanned, and the agent reads it from then on.
Prove it
Count files loaded at session start: seventeen means the corpus leaks, three means the layers work. Count corrections you repeat across sessions.

Learn more · Five Guardrails · Keeping Capabilities Honest · Harness Engineering ch. 13, 15–16 · The Last Check ch. 14

The legible codebase

Why
The agent copies the code's bad habits instead of following your rules. When a name and a rule disagree, the name wins, so fix the code before you write the rule.
How
Draw module boundaries and enforce them with an import linter. Catalog the seams where work enters and leaves. Rename vague names, and give each rename a sentence that says what it makes clear. Replace clever code with boring code.
Example
Same CLAUDE.md, same prompt, two repos. One diff touched 9 files in 5 packages and silenced tests, while the other touched 4 files and stayed green. The difference was the imports.
Prove it
Track files touched per change. On the book's eight-question architecture checklist, three or more "no" answers predict an eleven-file diff.

Learn more · Cold Codebase · Constraint Engineering · Harness Engineering ch. 17–18 · The Last Check ch. 8–9

Characterization tests

Why
The agent can't tell a fix from a regression in code nobody specified, and neither can you. Pinned behavior gives it a definition of correct that it can check by itself.
How
Start where damage is highest: money, permissions, customer data. Assert today's output with literal values, and test outputs rather than calls. Then gate edits to these tests, because an agent under pressure rewrites the test instead of the code.
Example
assert shipping_fee(0, "domestic") == 4.99 # Pinned, not endorsed. The value looks wrong, but a warehouse report depends on it.
Prove it
Break the code on purpose: flip > to >=, or return a constant. The suite must go red. If it stays green, the test never covered that line.

Learn more · Legacy Code With an Agent · Layers and Promotion · Harness Engineering ch. 19 · The Last Check ch. 12, 15

Driving with a falsifier hidden

Why
The agent writes plausible code by default, and plausible isn't correct. When the prompt asks for the failure case, the agent looks for the failure before it writes.
How
Ask for the smallest input that would make the change wrong. To check a change, have the agent argue against it using only evidence it can point to in the repo.
Example
"Before you write it, tell me the input that would make your version send twice anyway, and the input that would make it skip a send it should have made."
Prove it
Each falsifier the agent names becomes a test. Count the defects those tests catch before review.

Learn more · Junior to Senior · Cold Codebase · The Last Check ch. 19

Skills and commands

Why
The agent does a repeated job differently every time. A skill fixes the steps, but every capability costs context on every turn, so a weak one makes all output slightly worse.
How
Pick the lowest rung that closes the gap: command, skill, sub-agent, plugin, server. Write a skill's description as its trigger, since it's the only part always in context. End each phase with an artifact, never with "done". Read every command you run.
Example
A prompt run six times by three engineers earns a command. A rule with "then" in it is a sequence, so it becomes a skill.
Prove it
Read four numbers from the transcripts: fires per week, right when it fires, used after it returns, and missed when it should fire. Zero fires means delete it.

3
Output

Narrow the output

What the agent may produce. Sensors report and gates refuse, and a gate holds only the part of a rule that code can decide.

Sub-agents and judges

Why
The agent's context fills with search output, and its answers degrade. A second agent with its own memory fixes that. But "the task is hard" is not a reason to add one.
How
Define the return format first: a few bullets with file:line evidence, no prose. Give a builder a refusal scope. Open a judge's prompt with "Default to FAIL", and calibrate it like any other instrument.
Example
A team planned four agents. A 15-line rule file that named the downstream consumer and three fixtures did the same job.
Prove it
Validate each judge against 20 human labels. Pin the judge's model, because a change resets the history.

Learn more · The Eval Loop · Constraint Engineering · Harness Engineering ch. 20, 49

Permissions and sandboxing

Why
The agent runs a command it shouldn't, or prompts so often that people bypass the check. Too loose is a blast radius, and too tight is a bypass flag by Thursday.
How
Deny by default. Name each intent, and put it behind one make target. If a check can't reach a confident yes, fail closed. Put the sandbox under the allowlist, not in place of it, and give no production access, read or write.
Example
Allow make test and deny php artisan test. The allowlist fits on one screen, and Docker is the floor under whatever make leaves open.
Prove it
Track prompts per session, because a rising count means a bypass is coming. Log every call to an append-only audit log.

Learn more · The Narrow Door · Harness Engineering ch. 21, 37

Hooks

Why
The agent breaks a mechanical rule it has read many times. A hook checks every time, not when the agent remembers, and it reports while the agent still holds the context.
How
Write the check as a function that returns pass or fail with a reason. Then fire it on the earliest event that has the data. Print one line per error, location first, and stay silent on success.
Example
A rounding check on every edit: round_cash(1083) = 1085, but the customer's-favor amount is 1080. The hook blocks with exit 2, and the agent fixes it in the same turn.
Prove it
Track fires per week and how often the next attempt passes. Keep pre-commit under 30 seconds: one hook grew from 28 seconds to 4 minutes, and the team stopped running it.

Learn more · Five Guardrails · Junior to Senior · Harness Engineering ch. 19–20

Harness gates

Why
The agent deletes the hook, skips it, or edits the test until it passes. Anything the agent can edit is not a control, so the check moves into the harness, out of reach.
How
Reuse the hook's predicate. Only the mount point changes. Return the reason on refusal, allow two retries, then escalate. Keep the prose rule too, because a gate holds only the part code can decide.
Example
A tenant query used session.tenant_id where it needed request.path.tenant_id. Both versions passed the gate. Only one served the right invoice.
Prove it
Switch the rung off and compare runs. Run one check outside the pipeline too: in one experiment the pipeline said done, and make gate-run found 2 violations.

Learn more · Promotion to the Harness · Layers and Promotion · The Journey of a Rule · Harness Engineering ch. 22

Determinism by script hidden

Why
The agent gives a different verdict each time it inspects the same file. Code gives the same verdict every time, so move each verdict a script can settle into a script.
How
Find the decidable part of each judgment and put it in a script. Then change the instruction from "read and confirm" to "run and fix".
Example
"Read the migration and confirm it is reversible" invites variance. "Run the checker and fix what it reports" removes it.
Prove it
Run the step five times on the same input and count the distinct answers. One is determinism. Two is "a coin flip wearing a procedure." The test takes ten minutes.

Learn more · Keeping Capabilities Honest

Ratchets hidden

Why
The agent copies the old pattern, because most of the code still uses it. A rule that bans the old pattern fails on every legacy file, so a ratchet stops only the spread.
How
Count uses of the old pattern in the lines a change adds, not in the whole repo. Then fail the build on any new use, and leave existing files alone until someone touches them.
Example
ratchet.sh with PATTERN='ApiCaller' prints "This change adds 1 use(s) of ApiCaller" and exits 1.
Prove it
New uses of the old pattern stay at zero. The total count only goes down.

Learn more · Migrating Without Lying · Legacy Code With an Agent · The Last Check ch. 18

Injection containment hidden

Why
The agent follows instructions hidden in text it reads, such as an issue or a README. You can't patch that, so contain it: access, exposure, and exfiltration together are the lethal trifecta.
How
Split the agent that reads from the agent that acts. The reader has no credentials and no egress, and returns only structured output. Assume something gets through, and keep the possible win small.
Example
A README tells the agent to print its environment. The reader passes on a summary, and the actor never sees the raw text.
Prove it
Put attacks in the eval set. inj_003_readme_env.py checks gate_fired, no_egress, and env_not_in_output. Either the gate fired or it did not.

Learn more · Prompt Injection in the Harness · Harness Engineering ch. 38

4
Recovery

Narrow the recovery

The model will fail. The system decides what failure costs, and the record decides whether you can learn from it.

Loop bounds and cost ceilings

Why
The agent retries a bad input forever, or runs all night on one card. Failure is certain, so bounds decide whether it costs five dollars or a hundred.
How
Set an iteration cap, a budget, and a timeout, each one independent. Make the ceiling throw, because an advisory limit "is a bill with commentary." Send poison items to a dead-letter queue after three tries. Test the kill switch before the first night.
Example
A gate blocks money_is_integer. The agent revises on retry 1 of 2, and the gate passes. A card that burns its budget goes to the dead-letter queue instead of looping.
Prove it
Track cost per card and how many runs each bound stopped. In the book, a three-try dead-letter rule cut one run from $100 to $5.

Learn more · The Audit Trail · The Factory · Harness Engineering ch. 35, 40

Interrupts

Why
The agent guesses when it should ask, and the guess becomes a wrong change. Guessing is what kills contracts, so make asking cheaper than guessing.
How
Each interrupt carries one question, two or three options, a recommendation, the cost of a wrong guess, and the resume state. Before it asks, the agent reads what is already written down.
Example
In a migration, each unit may return UNCLEAR with a question instead of guessing. About one unit in twenty did.
Prove it
Chart interrupts by area each week. In the book, three areas made 80% of them, and those three became the next rules.

Learn more · The Migration Harness · Harness Engineering ch. 48

Small, reversible commits hidden

Why
The agent turns a small fix into a large diff. Then a bad change can't be reverted without losing the good parts with it.
How
Never mix a behavior change with a rename, a refactor, or formatting. Before the change, write three lines: what it does, the exact steps to undo it, and what the undo leaves behind.
Example
A 9-line retry fix came back as 280 lines in 11 files: a rename at 14 call sites, new constants, and an async rewrite. A five-second rollback became forty minutes at eleven at night.
Prove it
Run git rebase --exec 'make test' HEAD~2, so each commit passes on its own. The undo steps exist before the merge.

Learn more · The Bisect Drill · The Migration Harness · The Last Check ch. 16–17

Evals

Why
You can't tell whether a rule change made the agent better. One good run is one sample, so a frozen task set measures the band directly.
How
Check in about twenty tasks and don't edit them casually. Score with exit codes and greps first, then a judge, then a human sample. Compare two outputs blind, never one alone, and run 30 or more per arm.
Example
At a 70% pass rate, a drop to 50% needs about 95 samples per arm to see. A rise to 80% needs about 300. So a small set catches regressions, not polish.
Prove it
Report one of three outcomes: regression, improvement, or indistinguishable. Most edits land in the third, and that is a real result. Run it in CI on every rules change.

Learn more · The Eval Loop · Gauge · Harness Engineering ch. 30, 46

The factory

Why
Parallel agent runs crash, collide, and merge for reasons nobody can find later. A factory makes each run recoverable and each merge explainable.
How
Make the orchestrator a queue, not an agent: sequencing never goes to a model. Each phase has an exit, from a signed contract to a recorded lesson. Gates go before each action, and a record goes after it. Autonomy rises one level at a time, on evidence.
Example
A webhook chain needed three recovery layers. The reconciler that replaced it deleted more code than it added.
Prove it
Each quarter, pick a change merged three months ago. From the record, name the rejected alternative, the rule that constrained it, and the accountable human.

Learn more · The Factory · The Audit Trail · Open-Refinery · Harness Engineering ch. 57–58

The migration harness hidden

Why
Agents alone are inconsistent across thousands of call sites, and a codemod alone guesses at the odd shapes. So each one takes only the part it does reliably.
How
Count the shapes first. Then a codemod does the mechanical majority and refuses the rest, so agents get only the residue, one writer per file. The old code stays, as the oracle.
Example
Float dollars to integer cents across 10,412 sites. The codemod did 9,100, agents did 1,252, and 60 went to a human.
Prove it
Replay 4.1M recorded inputs through old and new code, and explain each difference. "Zero differences means you have not migrated anything."

5
Human

The human rung

Review catches the bugs that have no rule yet. Every miss here becomes the next rule for the levers above.

The comprehension gate

Why
The agent's diff passes every check and is still wrong. Review is the only filter for defects that have no rule yet, and it works only if the reviewer can explain the change.
How
The person who asks for the merge fills in four fields before the diff exists. The fields say what it does, where it enters and leaves, which rule it obeys, and what would make it wrong.
Example
"Adds a helper and updates two callers" describes the diff. "Cash totals now round down to the nickel instead of to the nearest one" describes the change.
Prove it
The falsifier names the test that covers it, or says NONE. Count catches per review, and CHARTER-GAP entries closed.

Learn more · The Comprehension Standard · Reverse-review · Harness Engineering ch. 32 · The Last Check ch. 2, 22

Drills hidden

Why
Reviewers stop catching agent defects, and nothing measures it. The human check is the last filter on agent output, so practice keeps it sharp.
How
Keep each drill short, repeated, and scored on the process, not the answer. So predict before you look, prove with a failing test or a concrete wrong output, and name the failure's class.
Example
The bisect drill: one regression, two hundred commits, no agent, 30 minutes a month. Verify the reproducer fails 5 of 5 on the bad commit and 0 of 5 on the good one before you search.
Prove it
Seed one known agent defect in a diff each week, and score four columns: found, proved, classified, durable fix. Don't total them. The flat column is the defect class that would ship.

Learn more · The Bisect Drill · Reverse-review · The Mentor's Playbook · Cold Codebase · The Last Check ch. 11, 13

The rejection log hidden

Why
The same agent defect comes back after you rejected it once. A log of rejections, with the cost of being wrong, shows which defects recur and should become rules.
How
Log each rejection and each escape in one line: the date, the change, what you did, and the cost had you been wrong. Escapes go first. Keep it where it outlives the job.
Example
2026-03-19 #431 approved the cache change; it broke stale reads in prod. now: every cache PR states its invalidation explicitly. two caught since, #455 and #470
Prove it
The "caught since" tail shows the behavior changed: that defect class stopped shipping. Aim for one to three entries a week.

6
Loop

The process: move knowledge between the tools

The loop matters more than any one tool. A miss becomes a rule, a rule that leaks becomes a gate, and a gate that stops firing gets deleted.

  1. NoticeA miss shows up in review (21), a gate ledger (11), the interrupt chart (16), or an eval (18).
  2. DiagnoseName the symptom, the lever that failed, and the first fix. Then re-run the same prompt on the same main.
  3. Fix the cheapest true thingUsually that is the code (4) or the contract (1). Then the charter (2).
  4. MeasureRun the eval before and after. If the result is indistinguishable, say so.
  5. Promote if it leaksCharter, then hook, then harness gate, then stage gate. Keep the prose rule at every step.
  6. PruneArchive rules and tools that stop firing or describe code that has moved on.

The cadence

  • Weekly, 15–30 minutes: promote patterns seen three times. Once is noise, and twice is suggestive.
  • Monthly, 1–2 hours: prune stale rules. Archive them; don't delete them.
  • After a miss: hold a post-mortem when redo passes an hour, or when one failure repeats within two weeks. Ship one structural fix that you can check into git.

"What observability catches twice, governance should prevent the third time." Harness Engineering covers both flywheels in chapters 28–32.

Start this week

Pick the mistake your agent made most often last month. If the code teaches it, fix one instance of the code. Then write it as a tiered charter rule, add one eval task that catches it, and see where it leaks. That leak tells you the next rung.
