Put the guardrail on the other side of the boundary.

Every discussion of agent constraints eventually reaches the same shrug: write it in the charter, and hope. This workshop builds a coding agent where the rule lives somewhere it cannot be talked past — in a different process from the loop that wants to break it — and then does the part nobody does, which is measuring which layer actually caught anything. One rule, five rungs, six nodes, and a report willing to tell you to delete a rung.

The question

Five places to put one rule, and only one of them is right

The rule is a sentence: money is integer cents, never float. It could live in the system prompt, in the tool list, in the tool itself, in a stage gate, or in CI. It can live in all five. The interesting question is not how to enforce it — it is which layer is carrying it, and how you would find out that you chose wrong.

rung 0 charter/money.md rung 1 tools_allowed rung 2 tools::write_file rung 3 gate-worker rung 4 make gate

Each rung catches something the rung above it structurally cannot, and each one costs something the rung above it does not. That trade is the whole subject. A charter generalises to cases you never enumerated and loses to an explicit instruction. A gate cannot generalise at all and cannot be argued with. Neither is the answer; knowing which one is doing the work is.

Three of those five mount the identical forty-line predicate. Rung 0 quotes it in prose and rung 1 is a different mechanism entirely — a capability, not a check. That asymmetry matters later, because it is why rung 0 is the only rung whose contribution can be measured in isolation.

The promotion test, and it disqualifies most rules

A rule earns a mechanical rung only if it is consequential (being wrong costs something, silently), recurrent (it has been broken more than once, by different people), and decidable (a machine can settle it). The third one is where most candidates die. "No float in the money module" is a predicate over a syntax tree. "Use ports and adapters" is not, and no amount of promotion will make it one.

1
The shape

Six nodes, and exactly one of them holds a loop

Writing code is the only stage whose shape is not knowable in advance — how many files it must read, how many times it must run the tests. Everything else is a transformation that happens to use a model, and giving those a loop buys nothing but cost.

py planner · coder · tools · policy · gate ts api trigger durable:subscriber

The wiring is not in any node's source. planner-worker does not know coder-worker exists; it publishes to code.implement and stops caring. The graph lives in four durable subscriptions, and the engine is the only thing that holds the whole picture — which is also why the console can draw it and why a crash mid-run leaves the handoff sitting on a queue instead of evaporating with a transcript.

What this shape costs

  1. Failures land somewhere A broken gate is a broken node, with a topic and a job id — not a paragraph somewhere in a long transcript.
  2. Retry is per-step A repair re-runs the coder against an existing workspace. It does not re-plan and it does not re-read the repository from scratch.
  3. The stages are fixed This pipeline cannot decide it needs a seventh stage. You chose the stages when you drew the graph.
  4. The honest case against If the work varies in structure from run to run, one agent with good tools beats a fixed graph, and no amount of durability makes up for a topology that does not match the problem.
Not a wrapper

The agent loop here is about forty lines of the Anthropic SDK's tool runner. It is not Claude Code, and it is not a framework's agent abstraction. That is deliberate: the entire argument of this workshop is about where the tool boundary sits, and you cannot make that argument inside a harness that already owns the tools for you.

2
The predicate

One implementation, and it takes text rather than a path

Three rungs enforce this rule. If there were three implementations, they would disagree within a month, and the agent would learn that some edits are free at one rung and blocked at the next. There is one, exposed once, as a function.

fn policy::check file policy/check.py escape # money-gate: allow

The constraint that makes this work is the one that looks like an accident: it imports nothing from the rest of the repo. The moment check() imports the iii SDK, it can only run where iii runs, and three of its mounts stop working. Keeping it dependency-free is not tidiness. It is what makes it mountable.

Text, not paths

policy::check takes {files: [{filename, source}]}. It never opens a file. That is the difference between a predicate that works when the policy node is a microVM on another host and one that quietly requires a shared filesystem nobody wrote down. It is also why the TypeScript node can enforce the identical rule without a line of Python:

Leave the door, and count who uses it

A guardrail with no sanctioned path produces creative circumvention — the agent that cannot divide invents a helper module whose name your scope glob misses. So the refusal message names the escape explicitly. Then watch the allow markers: a spike in them is the signal that the rule is wrong, not that the agents are.

3
Rung 1

The cheapest constraint is a tool the agent never received

A refusal is something to argue with. A capability that was never granted is not. The planner decides, per task, whether this job involves writing files at all — and a read-only task never holds write_file.

field tools_allowed flag writes_code

The coder node then builds its tool list from that field. Ask it to explain how split_evenly avoids losing a cent and it gets three tools; ask it to change the function and it gets four. There is no path by which an explanation task edits a file, and no deny rule had to be written to achieve that.

The same idea, one level up

The dashboard tab is a worker too, and it connects to a separate RBAC-gated listener whose expose_functions allowlist contains exactly one function id. The board cannot call tools::write_file — not because something refuses it, but because that function is not on its menu either.

4
Rung 2

The component that would have to be persuaded is not the one holding the pen

This is the rung a distributed runtime buys you and a single-process agent cannot. The check does not run inside the loop that wants to write. It runs in a different process, on the far side of the tool call, and it returns written: false.

fn tools::write_file calls policy::check

In a monolithic agent, a pre-write check is a function the agent's own loop calls before writing. The loop holds the pen; the check is advice, and a sufficiently stuck agent reasons its way past advice — "just this once, to see the shape." Here the loop holds four function ids belonging to someone else.

The agent's side of that boundary is four @beta_tool shims, each one worker.trigger deep. The coder node reads no files, writes no files and runs no commands. Strip the tools and it can do nothing at all — which is the property you want when the question is "what can this thing reach."

Why the refusal reaching the agent matters as much as the refusal

Rung 2 fires mid-turn, while the agent still has the whole task in context. In the runs below, both refused jobs recovered inside the loop and finished with zero repair passes. A gate that fires after the loop ends costs a re-run; a gate that fires during it costs a tool call. Same rule, two orders of magnitude apart in price.

5
Rung 3

The gate does not read the report, and the loop has a ceiling

Rung 2 sees only writes that went through tools::write_file. Rung 3 walks the tree as it actually is, and re-runs the tests itself. A reported success whose evidence is invisible in external state did not happen.

node gate-worker env GATE_MAX_ATTEMPTS=2

collect() takes every .py file in the workspace, not the files the agent said it touched. Those differ more often than you would like: a file arrives by a path nobody anticipated, a scope glob misses a filename, a new tool forgets to call the predicate.

When rung 3 catches something, do not add a rung 6

A catch at rung 3 is not a success story, it is a hole at rung 2. Ask how the violation got there — which write bypassed the tool, which filename the scope missed — and fix that. Adding a rung below a leaking one is how harnesses accumulate gates nobody can justify.

The brake

Two repair attempts, then blocked, then a person. A repair loop with no ceiling is not a self-healing system; it is a bill. And a loop that cannot converge in two passes is usually a task whose spec was wrong, not a budget problem — so read the workspaces that spent the ceiling before you raise it.

6
Observing it

Two surfaces, two different questions

The console answers what is running and what did it do. The rung board answers where was the rule actually enforced, and does that justify the rungs I am paying for. You want both, and only one of them is your job to build.

cli iii console worker iii-observability page :3111/dashboard

Observability is a declared worker, not a service you stand up. Five lines in config.yaml and every node's Logger lands correlated with the span that emitted it, so a run is one trace tree across six processes rather than six unrelated log streams. iii console reads it.

The board is the part worth building yourself, because it is the only view that knows what a rung is. It is served from /dashboard, and the page then connects back to the engine on the browser listener as a worker in its own right, polling board::summary — the one function it is allowed to call.

Instrument the rungs, not just the runs

Every refusal writes a rung_event — which rung, which node, which file, which findings — into the job, and the gate appends the finished job to a provenance log. Without that, "we have five layers of protection" is a claim. With it, it is a count, and counts can go down as well as up.

7
The evidence

The prose rung contributed nothing, and something else was carrying the rule

Five runs is not a study. But the result was not the one I designed the rung table expecting, and the mechanism that produced it is not on the table at all.

make promotion env CHARTER=off

The ablation

Rung 0 is the only rung that can be switched off without changing anything else, which makes it the only one whose contribution is directly measurable. CHARTER=off removes the charter from the system prompt and leaves everything below it standing.

Asked for "a discount percentage like 12.5 percent" with the charter, the agent converted the interface to basis points and cited the existing tax_cents function as its reason. Asked the same thing without the charter, it did the same thing, for the same reason.

The prose was not carrying the rule. billing/invoice.py was. The seed repository is all integer cents, // never /, basis points instead of fractional rates, an explicit remainder in split_evenly — and the agent copied its neighbours. That is the least convenient possible finding for a rung table and the most useful one: the strongest constraint on what an agent writes is the code it is reading while it writes. You cannot install that rung. You can only own a repository that has it.

So what did fire

All four catches came from two runs where the task itself demanded a float field. The agent was not being careless; it was doing as it was told. That is the realistic failure mode, and it is the argument for rung 2 specifically: a prose rule loses to an explicit instruction, every time. The charter is a paragraph in the same context window as the request. written: false is not a paragraph.

It marked the ratio field with a reason — correctly, a ratio is not an amount — and then reached for Fraction so the arithmetic stayed exact and the value leaving the property was an integer. It did not rename the file to dodge the scope glob. It did not move the maths into a module the predicate does not watch. Given a door, it used the door.

And rung 3 is now a demotion candidate

Zero catches, because rung 2 caught everything first. The argument for keeping it is not "it might catch something" — that argument keeps every gate alive forever. It is specific: rung 2 only sees writes that go through tools::write_file, so the day a seventh tool touches disk without calling the predicate, rung 3 is the only thing between it and the tree. That is a real risk with a real trigger condition, so the rung stays and gets re-examined when the tool surface changes. Writing the trigger condition down is the difference between keeping a gate and forgetting to remove one.

8
Your turn

Three terminals, then break it on purpose

The interesting exercises are the ones that make a rung fail. Anyone can watch a pipeline succeed.

repo iii-harness-layers-and-promotion make engine · dev · console · task

Four exercises, in order of how much they will teach you

  1. Make rung 1 fire Ask a question instead of requesting a change: INTENT="explain how split_evenly avoids losing a cent". The planner sets writes_code: false and the agent never receives write_file. Confirm it in the console's function list, not in the log.
  2. Make rung 2 fire Ask for the rule to be broken: INTENT="add a discount_rate field to LineItem stored as a float like 0.125". Watch tools-worker refuse, and read what the agent does next — that recovery is the whole payoff of an in-loop gate.
  3. Make rung 3 fire Give tools-worker a second write path that skips policy::check — an append_file, say — and use it. Rung 2 will not see the write; the stage gate will. You have just reproduced, deliberately, the exact hole that justifies keeping rung 3.
  4. Break the ablation's conclusion Rewrite workspace/billing/invoice.py to use floats throughout, then re-run with CHARTER=off. If the finding above is right, the agent will imitate the floats and rung 2 will fire on nearly every write. That is the experiment I have not run yet, and it is the one that would settle what rung 0 is worth.

Swapping in your own rule

Replace the body of check() and point MONEY_PATHS at your own scope. The rungs do not change, because none of them know what the rule is. If your candidate rule cannot be written as a function from source text to a list of strings, it has failed the decidability test — and it should stay in prose, carried by review and by the code around it, which the last section suggests is where most of the work was happening anyway.

The one-sentence version

Put the mechanical rungs where the agent cannot argue with them, keep exactly one implementation of each rule, count which rung actually catches things — and be as willing to delete a gate as you were to add one.
